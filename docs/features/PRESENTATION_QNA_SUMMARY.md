# DAMARA 백엔드 핵심 기능 발표 Q&A 정리

## 1. 게시글 예외 처리

### 기능 목적

공동구매 진행 중 발생할 수 있는 가격 변경, 품절, 수령 정보 변경, 상품 파손 등의 문제를 기록하고 거래 관계자에게 공유하는 기능이다.

일반적인 게시글 신고보다는 **실제 거래 과정에서 발생한 문제를 공유하고 처리 상태를 관리하는 기능**에 가깝다.

### 지원하는 예외 유형

- `price_changed`: 가격 변경
- `sold_out`: 상품 품절
- `pickup_changed`: 수령 장소 또는 시간 변경
- `damaged`: 상품 파손, 누락, 불량
- `seller_cancelled`: 주최자 취소
- `other`: 기타 예외

### 예외 등록 제한 기준

- 게시글 작성자 또는 실제 공동구매 참여자만 등록할 수 있다.
- 거래와 관계없는 사용자는 `403 FORBIDDEN`으로 차단한다.
- `seller_cancelled`는 게시글 작성자만 등록할 수 있다.
- 존재하지 않는 게시글 또는 사용자의 요청은 `404`로 차단한다.
- 등록자 ID가 없으면 `400`으로 차단한다.
- 정해진 예외 유형, 심각도, 상태값만 허용한다.

### 입력값 검증

- 예외 사유: 필수, 최대 2,000자
- 표시 제목: 최대 200자
- 표시 메시지: 최대 500자
- 가격: 0 이상
- 영향받은 수량: 1 이상의 정수
- 사용자 ID: UUID 형식
- 심각도: `info`, `warning`, `critical`
- 처리 상태: `open`, `resolved`, `dismissed`

### 처리 권한

- 예외 상태는 게시글 작성자 또는 해당 예외 등록자만 변경할 수 있다.
- URL의 게시글 ID와 예외가 실제로 속한 게시글 ID가 다르면 요청을 거부한다.
- 예외 등록 시 작성자와 참여자에게 알림을 생성한다.
- 예외를 직접 등록한 사용자에게는 중복 알림을 보내지 않는다.

### 관련 API

```text
POST  /api/posts/{postId}/exceptions
GET   /api/posts/{postId}/exceptions
PATCH /api/posts/{postId}/exceptions/{exceptionId}/status
```

### 발표 예상 질문

#### 거짓 예외를 등록하면 어떻게 하나요?

현재는 실제 거래 관계자만 등록하도록 제한한다. 추후 증빙 이미지, 동일 예외 중복 방지, 관리자 검토 기능을 추가할 수 있다.

#### 일반 신고 기능과 무엇이 다른가요?

예외 처리는 거래 과정에서 발생한 문제를 공유하고 해결하는 기능이다. 사기, 욕설, 부적절한 게시글 신고는 별도의 운영 신고 API가 필요하다.

#### 예외가 발생하면 거래가 자동 취소되나요?

자동 취소하지 않는다. 실제 상황과 참여자 의사가 다를 수 있으므로 경고와 알림을 먼저 제공하고 후속 상태를 결정하도록 설계했다.

### 현재 보완 필요 사항

- 동일 예외 중복 등록 방지
- 증빙 이미지 첨부
- 관리자 검토 및 제재 기능
- 예외 처리 상태 변경 이력 저장

## 2. 신뢰점수 및 신뢰학점

### 기능 목적

거래 완료, 취소, 참여 취소 등의 행동을 기반으로 사용자 신뢰도를 관리한다.

백엔드는 계산을 위해 `trustScore`를 사용하고, 사용자 화면에는 대학 서비스 콘셉트에 맞춘 `trustGrade`를 우선 표시한다.

```text
trustScore: 내부 정책 점수, 0~100점
trustGrade: 사용자 표시 학점, 2.5~4.5점
기본값: trustScore 50점 = trustGrade 3.5점
```

### 신뢰학점 계산식

```text
trustGrade = 2.5 + (trustScore / 100 × 2.0)
```

| trustScore | trustGrade |
| ---: | ---: |
| 0 | 2.5 |
| 50 | 3.5 |
| 75 | 4.0 |
| 100 | 4.5 |

### 점수 증감 정책

| 이벤트 | 대상 | trustScore 변화 |
| --- | --- | ---: |
| 공동구매 거래 완료 | 작성자 | +10 |
| 공동구매 거래 완료 | 참여자 | +5 |
| 작성자가 거래 취소 | 작성자 | -5 |
| 작성자가 게시글 삭제 | 작성자 | -5 |
| 참여자가 참여 취소 | 참여자 | -3 |
| 참여자 노쇼 | 참여자 | -10 예정 |

`closed`는 모집 마감 상태이므로 점수를 변경하지 않는다. 실제 거래가 끝난 `completed` 상태에서만 완료 보상을 적용한다.

### 기술 처리 흐름

```text
거래 상태 변경 또는 참여 취소 발생
→ TrustService 호출
→ 기존 trustScore 조회
→ 정책 점수 증감 계산
→ 점수를 0~100 범위로 제한
→ users.trust_score 변경
→ trust_events에 변경 이력 저장
```

점수 변경과 신뢰 이벤트 저장은 DB 트랜잭션으로 묶여 있다.

### 신뢰 이벤트 기록 내용

- 점수가 변경된 사용자
- 관련 게시글
- 이벤트 유형
- 요청된 점수 변화량
- 변경 전 점수
- 변경 후 점수
- 변경 사유
- 발생 시각

이를 통해 사용자의 현재 점수뿐 아니라 **왜 해당 점수가 되었는지 추적할 수 있다.**

### 발표 예상 질문

#### 점수가 100점을 넘거나 0점 아래로 내려가면 어떻게 하나요?

항상 0~100 범위로 제한한다. 98점에서 10점을 받아도 100점으로 저장하며, 2점에서 5점이 감점되어도 0점으로 저장한다.

#### 같은 거래에서 점수를 반복 획득할 수 있나요?

전용 상태 변경 API는 완료와 취소 상태를 최종 상태로 처리하여 반복 변경을 일부 방지한다. 다만 신뢰 이벤트 자체의 고유 제약은 없어 추가적인 중복 방지 장치가 필요하다.

#### 노쇼는 누가 판단하나요?

현재 노쇼 감점 정책과 이벤트 유형만 정의되어 있으며, 노쇼 확정 API와 증빙 기준은 아직 구현되지 않았다.

### 현재 보완 필요 사항

- 사용자·게시글·이벤트 유형 기반 중복 반영 방지
- 노쇼 확정 권한과 증빙 기준
- 운영 DB의 `trust_events` 테이블 존재 여부 확인
- 신뢰도 변경 실패 시 재처리 작업
- 관리자 수동 조정 권한 제한

## 3. 사용자 설정 및 방해금지 모드

### 기능 목적

사용자가 받고 싶은 알림 종류와 방해금지 시간을 마이페이지에서 직접 설정하도록 지원한다.

사용자 설정은 `users` 테이블과 분리된 `user_settings` 테이블에 저장한다.

```text
users 1명 : user_settings 최대 1개
```

### 지원하는 설정

| 설정 | 역할 | 기본값 |
| --- | --- | ---: |
| `pushEnabled` | 전체 알림 수신 여부 | true |
| `chatNotificationEnabled` | 채팅 알림 수신 여부 | true |
| `postNotificationEnabled` | 공동구매 알림 수신 여부 | true |
| `marketingNotificationEnabled` | 마케팅 알림 수신 여부 | false |
| `quietHoursEnabled` | 방해금지 시간 사용 여부 | false |
| `quietHoursStart` | 방해금지 시작 시간 | 23:00 |
| `quietHoursEnd` | 방해금지 종료 시간 | 08:00 |

### 설정 처리 흐름

```text
설정 조회
→ 사용자 존재 확인
→ 기존 설정 조회
→ 설정이 없으면 기본 설정 자동 생성
→ 프론트에 필요한 설정값만 반환
```

```text
설정 수정
→ 변경할 설정만 전달
→ boolean 및 시간 형식 검증
→ 기존 설정 부분 수정 또는 새 설정 생성
→ 변경된 전체 설정 반환
```

### 시간 검증 기준

- `HH:mm` 형식만 허용한다.
- 시간은 `00:00~23:59` 범위만 허용한다.
- `23:00~08:00`처럼 자정을 넘는 구간도 저장할 수 있다.

### 관련 API

```text
GET /api/users/{userId}/settings
PUT /api/users/{userId}/settings
```

### 현재 실제 적용 범위

새 참여자 알림 생성 시 다음 설정을 확인한다.

```text
pushEnabled = false
또는
postNotificationEnabled = false
→ 새 참여자 알림을 생성하지 않음
```

다만 현재는 아래 설정을 저장할 수 있지만 모든 알림 발송 경로에 완전히 연결되지는 않았다.

- 채팅 알림 설정
- 마케팅 알림 설정
- 방해금지 시간
- 공동구매 완료·취소·예외 알림의 세부 필터링

### 발표 예상 질문

#### 방해금지 시간에는 중요한 알림도 사라지나요?

현재는 방해금지 설정을 저장하는 단계다. 향후에는 알림 기록은 DB에 저장하고 실시간 소켓 또는 외부 푸시만 지연하는 방식이 적절하다. 심각도가 높은 알림은 방해금지 중에도 발송하도록 예외 정책을 적용할 수 있다.

#### 전체 알림과 세부 알림 중 무엇이 우선인가요?

전체 알림 설정인 `pushEnabled`가 최우선이다. 전체 알림이 활성화된 경우에만 채팅, 공동구매, 마케팅 등 세부 설정을 확인하는 구조가 적절하다.

#### 알림을 끄면 알림 기록도 생성되지 않나요?

현재 일부 알림은 설정이 꺼져 있으면 알림 자체를 생성하지 않는다. 중요 알림 누락을 방지하려면 기록은 저장하고 실시간 전송만 차단하는 방식으로 개선하는 것이 적절하다.

### 현재 보완 필요 사항

- 모든 알림 생성 경로에서 사용자 설정 공통 확인
- 방해금지 시간대 계산 및 자정 통과 처리
- 채팅 알림 설정과 소켓 전송 연결
- 중요도에 따른 방해금지 예외 정책
- 사용자의 시간대 설정 지원

## 4. 발표용 종합 답변

> DAMARA 백엔드는 단순히 공동구매 게시글을 등록하는 기능을 넘어, 거래 중 발생한 문제를 예외 케이스로 기록하고, 사용자의 거래 행동을 신뢰학점에 반영하며, 사용자별 알림 설정을 저장할 수 있도록 확장했습니다. 권한과 입력값 검증, 점수 변경 이력, 사용자별 설정 분리를 통해 실제 서비스 운영에 필요한 기반을 마련했으며, 중복 이벤트 방지, 관리자 검토, 방해금지 실시간 적용은 후속 개선 사항으로 남겨두었습니다.
